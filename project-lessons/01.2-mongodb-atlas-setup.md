## 1.2.1 Why Atlas and Not a Local MongoDB?

**MongoDB Atlas** is MongoDB hosted in the cloud, run by the company that makes MongoDB. The free tier is genuinely free and is more than enough for your project.

| | Local MongoDB | Atlas (what we use) |
|---|--------------|---------------------|
| Installation | Install and run a server on every machine | Nothing to install |
| Your partner sees your data | No — separate databases | Yes, if you share a cluster |
| Works when you deploy to Render | No — Render cannot reach your laptop | Yes |
| Survives your laptop dying | No | Yes |
| Cost | Free | Free (M0 tier) |

The deciding reason is deployment. In Lesson 28 you put your backend on Render. Render is a server in a data centre — it cannot reach a database running on your laptop in Kathmandu. Atlas is reachable from anywhere, so the same connection string works in development and in production.

## 1.2.2 Log In to Atlas

Go to **https://cloud.mongodb.com** and sign in.

- **Used Atlas for BookMyRoom?** Log in with that same account. You do not need a new one.
- **New to Atlas?** Click *Sign up*, register with Google or an email address, and verify it.

When asked what you are building, any answer is fine — it only changes which tips Atlas shows you.

---

## 1.2.3 Create a Cluster (or Use an Existing One)

A **cluster** is your database server in the cloud.

**Already have one from BookMyRoom?** Use it. One cluster can hold many databases, so your final year project can live alongside your course work — you will separate them by database name in section 1.2.7.

**Creating a new one:**

1. Click **+ Create** (or *Build a Cluster*)
2. Choose the **Free** tier — labelled **M0**
3. **Provider**: AWS is fine
4. **Region**: pick the one closest to you — **Mumbai (ap-south-1)** is nearest to Nepal and will feel noticeably faster
5. **Name**: leave it as `Cluster0` or name it after your project
6. Click **Create Deployment**

It takes one to three minutes to provision.

> **Stay on M0.** The paid tiers offer a free trial and then start charging. M0 never charges and is plenty for a project database.

---

## 1.2.4 Copy the Connection String

1. On your cluster, click the **Connect** button
2. A dialog opens. Choose **Drivers** (older versions of the UI call this *"Connect your application"*)
3. **Driver**: Node.js, latest version
4. Copy the string shown in step 3 of that dialog

It looks like this:

```
mongodb+srv://<db_username>:<db_password>@cluster0.ab1cd.mongodb.net/?retryWrites=true&w=majority&appName=Cluster0
```

**Paste it somewhere temporary** — a scratch file or a note. It is a template, not a working string yet: `<db_username>` and `<db_password>` are placeholders you replace in section 1.2.7.

### Reading the string

| Part | Meaning |
|------|---------|
| `mongodb+srv://` | The protocol. `+srv` means Atlas looks the servers up via DNS |
| `<db_username>:<db_password>` | The database user you create next |
| `cluster0.ab1cd.mongodb.net` | Your cluster's address — yours will differ |
| `?retryWrites=true&w=majority` | Sensible defaults. Leave them |

---

## 1.2.5 Create a Database User

> **This is the step most people get wrong.** Your **Atlas account** (the email you log in to the website with) is *not* the same as a **database user**. Your application connects as a database user. They are separate things with separate passwords.

1. In the left sidebar, open **Database Access** (in newer layouts: **Database & Network Access → Database Users**)
2. Click **Add New Database User**
3. **Authentication Method**: Password
4. **Username**: something simple and lowercase — `futsalapp`, `bookingadmin`
5. **Password**: click **Autogenerate Secure Password**, then **Copy** it
6. **Database User Privileges**: choose **Read and write to any database**
7. Click **Add User**

### Save that password now

**Atlas will never show it to you again.** Paste it straight into your `backend/.env` (section 1.2.8) before you do anything else. If you lose it, come back here and use **Edit → Edit Password** to set a new one — you do not need to delete the user.

> **Avoid special characters if you set the password yourself.** A password containing `@`, `:`, `/` or `#` breaks the connection string, because those characters already mean something in a URL. Either use the autogenerated one, or stick to letters and numbers. See section 1.2.7 if you are stuck with one.

Already have a user from BookMyRoom? You can reuse it — as long as you still know its password.

---

## 1.2.6 Open Network Access

Atlas blocks every IP address by default. Until you change this, your app cannot connect no matter how correct your string is.

1. Left sidebar → **Network Access** (or **Database & Network Access → IP Access List**)
2. Click **Add IP Address**
3. Click **Allow Access from Anywhere** — it fills in `0.0.0.0/0`
4. Click **Confirm**

### What `0.0.0.0/0` actually means — be ready for this question

It means *"accept connection attempts from any IP address on the internet"*.

That sounds alarming, so understand precisely what it does and does not do:

- ❌ It does **not** make your database public. Anyone connecting still needs your database username and password
- ✅ It **does** remove the second layer of defence — IP filtering — leaving only the password

**Why we use it anyway:**

- Your home and campus IP addresses change, often daily. A pinned IP means your app mysteriously stops working tomorrow
- Render (Lesson 28) does not give you a fixed outgoing IP on the free tier, so there is no single address to allow
- Your college wifi will have a different IP from your home wifi

**So it is the right choice for this project**, and it is what almost every tutorial and free-tier deployment uses. But because the password is now your *only* protection:

1. Use the autogenerated password — long and random
2. **Never commit `.env`** (Lesson 02, section 2.5, and Lesson 03, section 3.5)
3. Your project database holds test data, not real customers' details

> **If an examiner asks "is that secure?"** — the honest answer earns more marks than a defensive one: *"It relies entirely on credential security rather than network restriction. For a production system I would restrict it to the deployment platform's IP range or use VPC peering. For a student project on a free tier with dynamic IPs, it is the standard trade-off."* That answer shows you understand the risk rather than being unaware of it.

## 1.2.7 Assemble Your Final Connection String

Take the template from section 1.2.4 and make three changes.

**Start with:**

```
mongodb+srv://<db_username>:<db_password>@cluster0.ab1cd.mongodb.net/?retryWrites=true&w=majority&appName=Cluster0
```

**1. Replace the username and password** with the database user from section 1.2.5 — angle brackets and all:

```
mongodb+srv://futsalapp:Xk9mPq2vNw8sLt4R@cluster0.ab1cd.mongodb.net/?retryWrites=true&w=majority&appName=Cluster0
```

**2. Add your database name** between the `/` and the `?`. This is the part almost everyone forgets:

```
mongodb+srv://futsalapp:Xk9mPq2vNw8sLt4R@cluster0.ab1cd.mongodb.net/futsalbooking?retryWrites=true&w=majority&appName=Cluster0
                                                                     ^^^^^^^^^^^^^
```

Name it after your project — `futsalbooking`, `restauranttables`, `clinicbooking`. Lowercase, no spaces.

> **What if I leave it out?** Mongoose connects to a database called `test` instead. Everything appears to work, and then you wonder why your collections are somewhere odd. It also means two projects on the same cluster write into each other. Always name it.

**3. Only if your password contains special characters**, percent-encode them:

| Character | Replace with |
|-----------|-------------|
| `@` | `%40` |
| `:` | `%3A` |
| `/` | `%2F` |
| `#` | `%23` |
| `?` | `%3F` |
| space | `%20` |

So the password `p@ss:word` becomes `p%40ss%3Aword`. This is the cause of most "bad auth" errors that look impossible to debug.

## 1.2.8 Put It in Your Backend

In your `backend/` folder from Lesson 02, open **`.env`**:

```bash
PORT=4001
MONGODB_URI=mongodb+srv://futsalapp:Xk9mPq2vNw8sLt4R@cluster0.ab1cd.mongodb.net/futsalbooking?retryWrites=true&w=majority&appName=Cluster0
CLIENT_URL=http://localhost:3000
JWT_SECRET=replace-me-with-a-long-random-string
```

**No quotes, no spaces around the `=`, all on one line.** A line break inside the URI breaks it.

And in **`.env.example`** — the file that *does* get committed — keep only the shape:

```bash
MONGODB_URI=mongodb+srv://<user>:<password>@<cluster>.mongodb.net/yourdb?retryWrites=true&w=majority
```

> **Check `.gitignore` before you commit.** `.env` contains a working database password. Committing it to a repository — even a private one — means anyone who ever gets access can read and delete your data. Lesson 03 section 3.5 covers this.

## 1.2.9 Prove It Works

Start your backend:

```bash
cd backend
npm run dev
```

You want to see:

```
MongoDB connected successfully
Server running on http://localhost:4001
```

If you see `MongoDB connection failed`, go to section 1.2.11 — the message tells you which of the five steps above is wrong.

### Seeing your data

Back in Atlas, click your cluster and then **Browse Collections**. It will say there are no collections yet — correct, because nothing has been saved. Create a record through your API (Lesson 02, section 2.12), refresh this page, and your database will appear with your documents in it.

This view is genuinely useful during your demo: you can show the examiner a booking appearing in the database the moment you submit the form.

## 1.2.10 One Cluster, or One Each?

You are two people sharing a project. You have a choice:

| Approach | How | Best for |
|----------|-----|----------|
| **One each** (recommended for development) | Each member has their own Atlas account and cluster, each with their own `.env` | Day-to-day work — you cannot break your partner's data, and you can each experiment freely |
| **Shared** | One member creates the cluster and adds a database user for the other | The final demo, so you both show the same bookings |

**The practical route:** work on your own clusters while building, then before your defence, agree one cluster for the demo and both point your `.env` at it. Because the connection string is only ever in `.env`, switching is a one-line change with no code edits — which is exactly why we kept it out of the code in the first place.

> **Do not share `.env` files over WhatsApp.** If you need to give your partner access to your cluster, add a database user for them in Atlas and let them build their own string.

## 1.2.11 When It Will Not Connect

| Error message | What it means | Fix |
|---------------|--------------|-----|
| `bad auth : Authentication failed` | Wrong database username or password | Check for a leftover `<` `>`; re-set the password in Database Access; percent-encode special characters (1.2.7) |
| `Could not connect to any servers in your MongoDB Atlas cluster` | Your IP is not allowed | Network Access → Add IP Address → Allow Access from Anywhere (1.2.6) |
| `MONGODB_URI is not defined` | No `.env`, wrong folder, or `dotenv.config()` runs too late | `.env` must be in `backend/`; keep `dotenv.config()` at the very top of `index.ts` |
| `querySrv ENOTFOUND` or `queryTxt ENODATA` | Your network blocks the DNS lookups `mongodb+srv://` needs — **common on college wifi** | See the note below |
| `option ... is not supported` | Mangled string, usually a line break | Retype it as one single line |
| Connects, but collections are missing | No database name in the URI, so you are writing to `test` | Add the name before the `?` (1.2.7) |
| It worked yesterday, not today | You allowed only your old IP, and it changed | Use `0.0.0.0/0` (1.2.6) |

### The campus wifi problem

`mongodb+srv://` requires DNS SRV and TXT lookups, and some college and ISP networks filter them. You get `querySrv ENOTFOUND` even though everything is configured correctly.

The BookMyRoom backend solves this — look at the top of `bookmyroom_app/booking-backend/src/index.ts`:

```ts
import dns from "dns";

// Point this process at Google Public DNS, which reliably serves
// the SRV / TXT records that mongodb+srv:// needs.
dns.setServers(["8.8.8.8", "8.8.4.4"]);
```

Put those two lines above `dotenv.config()` in your own `index.ts`. It changes DNS resolution for **your Node process only** — nothing else on your computer is affected. If you never see these errors, you do not need it.

## Key Takeaways
1. Atlas is MongoDB in the cloud — free on M0, and reachable from Render when you deploy
2. Your **Atlas login** and your **database user** are different things with different passwords
3. The password is shown **once**. Paste it into `.env` immediately
4. **Network Access `0.0.0.0/0`** is required because your IP changes — the password becomes your only protection, so keep `.env` out of git
5. Get the string from **Connect → Drivers**, then replace `<db_username>` and `<db_password>`
6. **Add your database name** between the `/` and the `?`, or everything lands in `test`
7. Percent-encode special characters in passwords — `@` becomes `%40`
8. `MONGODB_URI` lives in `.env` only; `.env.example` shows the shape with no real values
9. `bad auth` = credentials; connection timeout = IP allowlist. The message tells you which
10. On college wifi, `dns.setServers(["8.8.8.8", "8.8.4.4"])` fixes `querySrv ENOTFOUND`
